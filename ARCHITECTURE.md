# Архитектура

## Принципы, из которых всё вытекает

**1. Срок считает детерминированный движок, а не модель.**
Таблица `SLA_RULES` в `domain.py` — единственный источник правды. Каждое правило
несёт ссылку на норму, и эта ссылка доходит до интерфейса и до драфта ответа.
ИИ может уточнить *тип* обращения; дату он не считает никогда. Ошибка в сроке
по ФЗ-152 — это административная ответственность, такое нельзя отдавать
вероятностной модели.

**2. Правила работают без сети.**
Классификатор — взвешенные регулярные выражения по русскому тексту. Ключ к ИИ
не обязателен: без него доступны квалификация, сроки, флажки, OCR и драфты
по шаблонам. ИИ — слой сверху, его отказ не ломает работу.

**3. Неопределённость показывается, а не прячется.**
Приблизительный календарь, низкая уверенность классификации, спорная дата
начала срока, нераспознанное вложение — всё это видно в интерфейсе. Система
не делает вид, что знает больше, чем знает.

**4. Решение человека сильнее автомата.**
Ручная правка типа фиксируется как `classified_by = MANUAL` и переживает
повторный разбор. Флажки, снятые человеком, не возвращаются автоматически.

## Схема данных

```
LegalEntity ──┬── Inbox ────┐
              └── Service ──┤
                            ▼
                        Request ──┬── RequestFlag   (RED / BLUE, с обоснованием)
                                  ├── Attachment    (файл + извлечённый текст)
                                  ├── Draft         (текст ответа + чек-лист)
                                  └── Event         (журнал действий)

ResponseTemplate ─────────────────┘  (подбирается под Request)
```

`Request` хранит и распознанное автоматически, и подтверждённое человеком:

| Поле | Зачем |
|---|---|
| `inbox_email` | ящик получения — обязательный фильтр и признак адресата |
| `legal_entity_id` / `legal_entity_mentioned` | ЮЛ из справочника и ЮЛ как названо в письме — они могут расходиться |
| `service_id` / `service_mentioned` | сервис или бизнес-процесс |
| `identity_confirmed_at` | дата подтверждения личности; от неё может считаться срок |
| `manual_due_date` | срок из текста предписания, приоритетнее расчётного |
| `extension_applied` | продление на 5 рабочих дней |
| `due_date`, `urgency`, `has_red_flag`, `has_blue_flag` | денормализация ради быстрых фильтров |
| `classified_by`, `classification_confidence`, `classification` | как получен результат и на чём основан |
| `unconfirmed_fields` | что заполнено автоматом и ещё не подтверждено |

Денормализованные поля пересчитываются при каждой правке и раз в сутки
через `POST /api/maintenance/recalculate` — срочность меняется от хода времени,
а не только от действий пользователя.

## Расчёт сроков

```
тип обращения → SLA_RULES → набор Deadline
                                  │
   received_at ──┐                │
identity_confirmed_at ──┼─→ база отсчёта
                        │
                        ▼
         рабочие дни / календарные дни / часы / немедленно
                        │
      производственный календарь РФ (переносы)
                        │
                        ▼
      manual_due_date? → перекрывает    extension? → +5 рабочих дней
                        │
                        ▼
             ComputedDeadline + срочность
```

Особенности:

* **Немедленные обязанности** (блокирование по ч. 1 ст. 21, прекращение
  рекламной обработки по ч. 2 ст. 15) вынесены в отдельный список
  `immediate_actions` и не влияют на срочность строки в реестре — иначе любое
  требование об уточнении вечно висело бы как «истекает сегодня».
* **Основной срок** — ближайшая по дате точка. У отзыва согласия это ответ
  субъекту (10 рабочих дней), а не уничтожение (30 дней).
* **Год вне календаря** → `approximate = true`, предупреждение в карточке.

## Классификация

```
текст письма + тема + текст вложений
        │
        ├─→ кто обращается   (домен отправителя rkn.gov.ru + формулировки)
        │        └─→ гасит несовместимые типы: РКН не подаёт запрос субъекта,
        │            посторонний отправитель не присылает предписание
        ├─→ тип обращения    (взвешенные шаблоны + приор по тематике ящика)
        ├─→ вид субъекта     (трудовой договор → работник, резюме → кандидат…)
        ├─→ реквизиты        (ИНН, договор, срок из документа; номер паспорта
        │                     НЕ сохраняется — только факт наличия, ст. 5 ч. 5)
        └─→ флажки           (красные и синие, с обоснованием)
        │
   [опционально] ИИ уточняет тип и добавляет флажки
        │
   привязка ЮЛ (строгое совпадение) и сервиса (совпадение с учётом склонения)
```

Уверенность считается из абсолютного веса и отрыва от второго места: два
близких кандидата дают синий флажок `AMBIGUOUS_TYPE`, а не тихий выбор.

Сопоставление ключевых слов учитывает русское словоизменение, но с границами:
«мобильное приложение» находится в «мобильном приложении» и не находится
в «с приложением документов»; «заказ» не совпадает с «законом».

## Извлечение текста

| Вход | Путь |
|---|---|
| PDF с текстовым слоем | pdfminer.six |
| PDF-скан | poppler → изображения → tesseract (rus+eng) |
| Фото | автоповорот по EXIF, апскейл, оттенки серого, автоконтраст → tesseract |
| DOCX | python-docx, включая таблицы |
| XLSX | openpyxl |
| EML | разбор письма + рекурсивно его вложения, определение кодировки |
| Двоичные файлы, .doc/.xls | отказ с понятным объяснением, что делать |

PDF сначала пробуется как текст: OCR по документу с готовым текстовым слоем
даёт худший результат. Порог — 40 символов на страницу.

Всё, что не распозналось, помечается `needs_review` и правится вручную;
после правки обращение переразбирается.

## Драфты

```
Request + рассчитанные сроки + справочники
        │
        ├─→ ранжирование типовых ответов (тип > вид субъекта > заявитель > ЮЛ)
        ├─→ контекст подстановки, включая отдельную дату на каждую
        │   контрольную точку: {{СРОК ОТВЕТА}} ≠ {{СРОК ПРЕКРАЩЕНИЯ ОБРАБОТКИ}}
        ├─→ [опционально] ИИ адаптирует текст, сроки берёт готовыми
        └─→ чек-лист проверок перед отправкой
```

Незаполненный плейсхолдер не заменяется пустотой: он остаётся в тексте
как `[ИМЯ]` и попадает в список `unresolved_placeholders`. Ответ не должен
уйти с потерянным реквизитом.

## Интерфейс

Нативные ES-модули без сборки: `index.html` + `app.js` + `styles.css`.
Это осознанный выбор — система должна запускаться одной командой и не зависеть
от состояния npm-экосистемы через год. Тёмная и светлая темы на CSS-переменных.

## Что менять при развитии

* **Новый тип обращения** — добавить в `RequestType`, подпись в
  `REQUEST_TYPE_LABELS`, правило в `SLA_RULES`, шаблоны в `TYPE_PATTERNS`.
  Интерфейс подхватит его сам: фильтры и формы строятся из `/api/reference`.
* **Новый флажок** — добавить в `propose_flags` и покрыть тестом.
* **Новый год календаря** — дописать в `production_calendar.json` после выхода
  постановления Правительства. Это ежегодная обязательная процедура.
* **Многопользовательский режим** — сменить `DATABASE_URL` на PostgreSQL;
  аутентификации в системе нет, она рассчитана на запуск во внутреннем контуре.
